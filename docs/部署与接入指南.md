# 渊渟 FATHOM 部署与接入指南

> 版本：0.4 · 适用范围：FATHOM 企业语义运行时 · 更新日期：2026-08-25

本文面向实施、运维和平台管理员，说明如何运行、部署、配置 FATHOM，以及如何将其接入数据源、知识库、工作流和智能体平台。架构原理见《架构设计》，本文只保留可执行步骤、验收标准和故障定位方法。

部署完成的最低可用闭环为：

```text
服务健康 → 数据源/知识库接入 → 需求证据与对象身份 → 语义提炼与评审
        → MQL 确定执行 → 能力发布与受控动作 → 反馈、评测与回执
```

## 1. 部署前说明

FATHOM 默认使用轻量单体架构：FastAPI 提供页面和 API，Vue 页面已编译进服务，SQLite 保存语义、配置、会话、知识和治理记录，DuckDB 执行本地分析任务。企业事实数据可保留在原系统，由只读连接器访问。

部署 ZIP 包含源码、编译后的 Web 页面、安装与启动脚本、示例配置和文档；不包含 Python/Node 依赖、运行数据库、密钥、缓存、本地测试数据、介绍视频和外部平台运行卷。首次启动会自动创建空数据库和表，所以代码包可独立运行。包体较小是正常现象。

推荐环境：

- Python 3.12 或更高版本
- Windows 10/11、Windows Server 或主流 Linux 发行版
- 修改前端时才需要 Node.js 20+ 与 pnpm
- Lite 模式建议至少 2 核、4 GB 内存、5 GB 可用磁盘

## 2. Windows 运行与部署

解压部署包，在项目根目录打开 PowerShell：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
Copy-Item config\fathom.example.yaml config\fathom.yaml
.\scripts\install.ps1 -LiteOnly
.\scripts\start.ps1 -BindAddress 0.0.0.0 -Port 8000
```

浏览器打开 `http://服务器地址:8000`。本机使用 `http://127.0.0.1:8000`。

需要关系数据库、工业协议、图、向量或全文检索连接器时，执行完整安装：

```powershell
.\scripts\install.ps1
```

已编译页面随部署包提供。只有修改 `apps/web` 源码时才需要重新构建。

停止服务：在运行窗口按 `Ctrl+C`。健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/health
```

返回 `status: healthy` 才表示服务就绪。

## 3. Linux 部署

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e .
cp config/fathom.example.yaml config/fathom.yaml
.venv/bin/fathom init
FATHOM_CONFIG_FILE="$PWD/config/fathom.yaml" \
  .venv/bin/uvicorn fathom.main:app --host 0.0.0.0 --port 8000
```

需要全部连接器：

```bash
.venv/bin/pip install -e '.[connectors-sql,connectors-industrial,connectors-context]'
```

生产环境建议使用 systemd：

```ini
[Unit]
Description=FATHOM
After=network.target

[Service]
Type=simple
User=fathom
WorkingDirectory=/opt/fathom
Environment=FATHOM_CONFIG_FILE=/opt/fathom/config/fathom.yaml
EnvironmentFile=-/opt/fathom/config/fathom.env
ExecStart=/opt/fathom/.venv/bin/uvicorn fathom.main:app --host 0.0.0.0 --port 8000
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now fathom
curl http://127.0.0.1:8000/api/v1/health
```

建议在 FATHOM 前配置企业现有反向代理，由代理提供 HTTPS、域名、访问控制、请求体限制和日志策略。流式问数使用 SSE，代理必须关闭响应缓冲并允许长连接。

## 4. 项目配置

主配置文件为 `config/fathom.yaml`。可从 `config/fathom.example.yaml` 复制；生产环境参考 `config/fathom.production.example.yaml`。

```yaml
app_name: "渊渟 FATHOM"
environment: production
storage_profile: lite
database_url: "sqlite:///./data/fathom.db"
semantic_directory: "./semantic"
backup_directory: "./data/backups"
enable_duckdb: true
enable_vector_search: false
duckdb_memory_limit: "512MB"
duckdb_threads: 2
auth_enabled: true
```

配置优先级为：`FATHOM_*` 环境变量、`.env`、YAML、系统默认值。嵌套项使用双下划线。

| 内容 | 默认位置 |
| --- | --- |
| 运行数据库 | `data/fathom.db` |
| 一致性备份 | `data/backups/` |
| 语义契约 | `semantic/` |
| 主配置 | `config/fathom.yaml` |
| 编译页面 | `apps/api/src/fathom/interfaces/static/` |

Lite 模式适合单机、边缘节点和中小团队。需要多实例并发写、高可用或集中数据库运维时，将 `database_url` 切换到企业数据库，并使用相应驱动和备份体系。分析型大数据仍应留在原有计算引擎，FATHOM 保存语义、计划、证据和治理状态。

## 5. 配置大模型

模型用于自然语言理解、语义抽取、解释和跨模态理解；企业指标数值由已发布口径和确定性查询计算。

### 5.1 页面配置

1. 打开“系统设置”。
2. 新增模型服务，选择兼容协议。
3. 填写 Base URL，例如 `https://model.example.com/v1`。
4. API 模式选择“自动”。
5. 填写 API Key，点击探测。
6. 从自动发现列表中选择模型，也可手动输入模型 ID。
7. 调整 temperature、top_p、max_output_tokens 和超时。
8. 为规划、语义抽取、解释、视觉、嵌入和 Agent 分别绑定模型路由。

模型密钥通过操作系统凭证库保存，不在页面回显。无可用凭证库的服务器应使用环境变量。

### 5.2 YAML 与环境变量

```yaml
model_gateway:
  providers:
    - key: primary_reasoner
      name: 主推理模型
      provider_type: openai_compatible
      base_url: https://model.example.com/v1
      api_mode: auto
      default_model: model-name
      secret_reference: env://FATHOM_PRIMARY_MODEL_API_KEY
      enabled: true
      parameters:
        temperature: 0.1
        top_p: 0.9
        max_output_tokens: 4096
        timeout_seconds: 60
  routes:
    planner: primary_reasoner
    semantic_extractor: primary_reasoner
    explainer: primary_reasoner
    agent: primary_reasoner
```

Windows 当前会话：

```powershell
$env:FATHOM_PRIMARY_MODEL_API_KEY = '在此设置密钥'
.\scripts\start.ps1 -BindAddress 0.0.0.0
```

Linux 的 `/opt/fathom/config/fathom.env`：

```text
FATHOM_PRIMARY_MODEL_API_KEY=在此设置密钥
```

获取模型列表成功只说明目录接口可用；必须继续完成生成探测和黄金问题集评测。

## 6. 接入数据源与知识库

### 6.1 配置数据源

在“数据接入”中新建连接，保存后依次执行“测试连接”“发现结构”和“提炼语义”。FATHOM 内置 SQLite、DuckDB、CSV/JSON/Parquet 文件和 REST；完整依赖还支持 PostgreSQL、MySQL、SQL Server、Oracle、TDengine、MQTT、OPC UA、Redis、Elasticsearch、Neo4j 和 Qdrant。工业历史库通过厂商插件接入。

关系数据库示例：

```json
{"host":"10.0.0.20","port":5432,"database":"factory","username":"fathom_ro","schema":"public"}
```

TDengine 示例：

```json
{"endpoint":"ws://10.0.0.30:6041","database":"manufacturing","username":"fathom_ro"}
```

密码不写入连接 JSON，使用密钥引用：

```text
env://FATHOM_SOURCE_PASSWORD
```

生产连接必须使用专用只读账号，并在源端限制数据库、Schema、表、Topic、节点或接口范围。

### 6.2 一次性语义提炼

首次提炼会保存 Schema 快照，识别对象、属性、外键关系、事件表和指标候选，并把结果送入治理候选区。再次执行时先比较快照哈希：结构未变化返回 `unchanged`，不会重复创建候选；结构变化时返回表和字段差异。

```powershell
$baseUrl = 'http://127.0.0.1:8000/api/v1'
Invoke-RestMethod -Method Post -Uri "$baseUrl/data-sources/plant_source/extract"
Invoke-RestMethod -Uri "$baseUrl/semantic-extraction/runs?limit=20"
```

重点检查返回值：

- `status`：`candidates_created` 或 `unchanged`；
- `snapshot_id`：本次使用的结构快照；
- `diff`：新增、删除和类型变化；
- `candidates`：自动识别的语义资产候选；
- `governance`：已创建、跳过和冲突项。

自动提炼只产生 `candidate`，不会直接发布生产指标。尤其是 `sum`、`avg`、比率和单位推断，必须由业务 Owner 核对公式、粒度、时间口径和适用范围。

### 6.3 知识库导入

知识库支持页面录入和文件上传。文档保存后先按内容哈希去重并切块索引；只有检测到“指标、口径、计算公式、数据字典”等明确证据时才生成语义候选，普通制度和说明文档只进入检索。

导入结果中的 `semantic_extraction.status` 可能为：

- `candidates_created`：已识别并创建治理候选；
- `indexed_only`：只建立知识索引，没有足够证据生成语义；
- 已存在相同内容时返回 `deduplicated: true`。

### 6.4 跨系统语义运行时预接入

接入 PostgreSQL、MES、ERP 或已有 API 时，先完成四项准备：确定业务域和 Owner；整理 20–50 条可验收问题；为同一业务对象准备统一 ID 与各系统局部 ID 对照；收集代表性的 Schema、只读 SQL 和 OpenAPI 文档。不要先搬迁全部数据，也不要让大模型直接改写生产查询。

保存对象身份映射：

```powershell
$baseUrl = 'http://127.0.0.1:8000/api/v1'
$identity = @{
  canonical_object_id = 'line_01'
  source_key = 'postgres_runtime_demo'
  external_object_id = 'MES-L01'
  owner = 'data-owner'
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$baseUrl/runtime/object-identities" -ContentType 'application/json' -Body $identity
```

反向读取存量 SQL 或 OpenAPI 时调用 `/runtime/reverse-assets`。返回的表、字段、指标映射和能力均为评审候选；先核对来源、Owner、输入输出、权限和副作用，再保存映射或发布能力。

需求探索通过 `/runtime/requirements/explore` 生成来源引用、待澄清问题和潜在冲突，再使用 `/runtime/requirements/{requirement_key}/review` 完成评审。需求获批后再建立或发布语义资产，避免从字段名直接猜业务口径。

已发布指标可编译为稳定能力：

```powershell
$compile = @{
  metric_key = 'oee'
  owner = 'semantic-owner'
  minimum_role = 'viewer'
  publish = $true
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$baseUrl/runtime/capabilities/compile" -ContentType 'application/json' -Body $compile
```

编译后的 `semantic.metric.oee` 会进入能力目录，并通过 OpenAPI/MCP 暴露同一受控契约。建案和通知属于有副作用动作，必须同时满足角色、审批令牌和幂等键要求；执行记录可从 `/runtime/actions` 查询。

## 7. 接入 Dify

### 7.1 网络前提

FATHOM 监听 `0.0.0.0:8000`。当 Dify 运行在 Docker 中时，容器访问宿主机应使用 `host.docker.internal`，不能使用容器自身的 `127.0.0.1`。

```powershell
Invoke-RestMethod http://host.docker.internal:8000/api/v1/health
```

只有返回 `status: healthy` 才继续导入工具。

### 7.2 方式一：OpenAPI 工具 + Chatflow（推荐）

1. 打开 Dify 的“工具/集成 → 自定义工具”。
2. 新建工具，名称填写“FATHOM 语义问数”。
3. 选择“从 URL 导入”。
4. 输入：

   ```text
   http://host.docker.internal:8000/api/v1/integrations/dify/openapi.yaml
   ```

5. 开发环境鉴权可选“无”；生产环境配置 Bearer Token。
6. 保存后确认存在 `ask_data`、`ask_data_structured`、`search_enterprise_knowledge`、`search_semantics`、`get_object_context` 和 `run_controlled_agent_flow`。
7. 在工作室导入 `integrations/dify/fathom-chatflow.yml`。
8. 将工具节点重新绑定到当前工作区的“FATHOM 语义问数 / ask_data”，为 LLM 节点选择当前工作区可用模型，测试后发布。

Chatflow 提供连续对话。用户只填写自然语言问题，不需要输入内部对象 ID。企业数据不存在时，FATHOM 明确返回无可验证数据；概念、方法和一般对话可由 LLM 正常回答。

### 7.3 方式二：粘贴或上传 OpenAPI YAML

当 Dify 无法访问导入 URL 时，浏览器打开下列地址下载 YAML，再粘贴或上传：

```text
http://FATHOM服务器:8000/api/v1/integrations/dify/openapi.yaml
```

仓库文件为 `integrations/dify/fathom-openapi.yaml`。工具的服务地址必须改成 Dify 容器实际可访问的地址。

### 7.4 方式三：自建 Chatflow

```text
用户输入
  → FATHOM / ask_data（question = sys.query）
  → LLM（结合用户问题和工具文本组织回答）
  → 直接回复
```

LLM 规则应明确：企业数值只能使用 FATHOM 返回结果；无数据时不得补造；通用知识可以正常回答。

### 7.5 Workflow、Agent 与 HTTP

- Workflow：适合定时、批处理和被其他系统调用，不提供多轮聊天界面。
- Agent：适合自主选择语义搜索、知识检索、对象上下文和问数工具。
- HTTP 节点：无需注册工具，直接调用接口。

```http
POST http://FATHOM服务器:8000/api/v1/query/answer
Content-Type: application/json

{"question":"昨天的 OEE 是多少？"}
```

`/query/answer` 返回可直接展示的文本；`/query/ask` 返回计划、MQL、数据、证据、质量告警、trace 和可选 RCA；`/query/stream` 使用 SSE 流式返回。

### 7.6 消息与评价回传

结构化问数返回 `trace_id`，诊断问题还返回 `analysis_run_id`。上层平台生成最终消息并获得 `message_id` 后，由平台回调或中间层调用消息绑定接口（operationId 为 `link_external_message`）：

```http
POST /api/v1/integrations/external/message-links
Content-Type: application/json

{
  "provider": "external",
  "app_id": "manufacturing-assistant",
  "external_conversation_id": "external-conversation-id",
  "external_message_id": "external-message-id",
  "trace_id": "trace_xxx"
}
```

用户点赞、点踩或补充文字后，将评价导入（operationId 为 `import_external_feedback`）：

```http
POST /api/v1/integrations/external/feedback/import
Content-Type: application/json

{
  "app_id": "manufacturing-assistant",
  "conversation_id": "external-conversation-id",
  "message_id": "external-message-id",
  "rating": "dislike",
  "content": "不是一号线，我问的是二号线"
}
```

FATHOM 会保存来源、评分、文本情绪、错误类别、置信度和 trace。当前服务提供接收接口，不主动轮询上层平台；如果平台不能在评价事件后触发工作流，需要由网关、插件或定时同步任务转发评价。

## 8. FATHOM MQL 与可信问数

### 8.1 定位与命名

FATHOM MQL 是项目内部的结构化指标查询契约，不是 SQL，也不是 Google Cloud 的 Monitoring Query Language。对外文档和接口应使用完整名称“FATHOM MQL”，避免只写容易混淆的 `MQL`。

自然语言只负责生成候选计划，程序负责校验并调用固定模板：

```text
自然语言 → 对象/指标消歧 → FATHOM MQL → 权限与语义校验
        → 固定查询模板 → 参数化 SQL/连接器调用 → 证据化结果
```

典型 MQL：

```json
{
  "metric": "order_fulfillment_rate",
  "object_ids": ["line_01"],
  "dimensions": ["production_line", "day"],
  "filters": [],
  "time_range": "yesterday",
  "comparison": "previous_period",
  "limit": 2,
  "semantic_version": "0.2.0"
}
```

LLM 不得直接提交 SQL。指标未发布、对象歧义、非法维度、越权、非法操作符或时间无法解析时，MQL 校验器必须阻断执行。

### 8.2 结果状态

| 状态 | 含义 | 上层处理 |
| --- | --- | --- |
| `verified` | 查询已通过语义、权限和执行验证 | 可展示数值与证据 |
| `verified_no_data` | 查询合法，但时间范围内没有事实数据 | 展示无数据，不补造 |
| `needs_clarification` | 对象、指标或范围不唯一 | 向用户澄清 |
| 拒绝/阻断 | 越权、未发布口径或非法查询 | 展示拒绝原因，不重试猜测 |

每次结构化回答至少记录 `trace_id`、`semantic_version`、`data_freshness`、MQL、编译模板和证据。生产验收不能只检查答案文字，还要检查这些字段。

## 9. 根因分析

### 9.1 触发与执行链

当前版本在问题包含“为什么、原因、下降、异常”等诊断表达时，把计划意图设为 `diagnose_metric`。系统仍然先执行 MQL 校验和指标查询，只有获得真实观测值后才进入 RCA：

```text
confirm_anomaly → decompose_metric → rank_contributors → validate_hypothesis
```

四个步骤分别完成：

1. 确认当前值、上一期值和变化量；
2. 从已发布公式识别可分析因子；
3. 查询对象及相关对象的同期事件，并按持续时间排序；
4. 校验对象和时间一致性，保存证据与反证。

### 9.2 结论等级

| 等级 | 使用条件 | 对外措辞 |
| --- | --- | --- |
| `driver` | 已确认变化，但事件证据不足 | 驱动因素/尚待调查 |
| `suspected_cause` | 变化与同期事件相关，但未证明因果 | 疑似原因 |
| `verified_root_cause` | 事件包含明确因果核验标记、原因和有效持续时间 | 已验证根因 |

普通事件相关不能自动升级为已验证根因。未达到因果条件时，结果中必须保留“相关不等于因果”的 `counterevidence`。

### 9.3 查询分析回执

`/query/ask` 返回的 `analysis_run_id` 用于读取完整分析过程：

```powershell
$runId = 'rca_xxxxxxxxxxxxxxxx'
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/analysis-runs/$runId"
```

回执包含 `trace_id`、指标、对象、变化量、步骤状态、贡献事件、证据数量、反证和结论等级。运维排障时先看步骤状态：`insufficient_data` 表示数据或事件不足，不应通过 Prompt 强行生成结论。

### 9.4 当前边界

当前 RCA 是可审计的规则化证据链，不是完整因果推断平台。公式步骤目前识别因子，但尚未计算每个因子的定量贡献；事件默认读取最近四天并按持续时间排序；`verified_root_cause` 依赖业务系统或人工提供 `causal_verification` 标记。需要反事实、对照组、因果图和多跳传播时，应接入专用分析流程，再把核验结果写回 FATHOM。

## 10. 接入其他平台

FATHOM 不依赖某个上层产品，提供三类通用入口：

- OpenAPI：`/openapi.json` 和 `/api/v1/*`
- MCP：`POST /mcp`
- A2A：`/.well-known/agent-card.json` 和 `POST /a2a`

支持 MCP 的智能体软件可配置：

```json
{
  "mcpServers": {
    "fathom": {
      "type": "streamable-http",
      "url": "http://FATHOM服务器:8000/mcp"
    }
  }
}
```

上层平台只获得受控工具结果，不需要保存企业数据库、TDengine、MQTT 或模型密钥。

## 11. 权限、备份、升级与打包

生产环境开启 `auth_enabled`，生成令牌摘要：

```powershell
.\.venv\Scripts\fathom.exe token-hash "一段足够长的随机令牌"
```

原始令牌由调用方保管，配置文件只保存摘要。调用时使用 `Authorization: Bearer <token>`。为上层平台、BI 和运维脚本分别创建主体，不共用管理员令牌。

升级流程：创建一致性备份；停止服务；保留 `data/`、`semantic/`、生产配置和环境变量；替换程序并安装依赖；启动后检查健康接口、数据源、模型、上层平台工具和黄金问题集；异常时恢复备份。

生成发布包：

```powershell
pnpm --dir apps/web build
.\scripts\package-release.ps1 -Version 0.4.0
```

脚本基于当前 Git 工作区生成 ZIP 和 `.sha256`，并排除 PDF、DOCX、PPT/Excel 二进制、音视频、运行数据库、密钥、缓存、依赖和外部平台数据卷。发布前必须从 ZIP 内部反向检查必要代码与 Markdown 文档存在，并校验 SHA256。

## 12. 上线验收

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/health
.\.venv\Scripts\python.exe -m pytest apps/api/tests -q
pnpm --dir apps/web test -- --run
pnpm --dir apps/web build
```

最低验收项：

- 数据源能测试、发现真实结构，并生成或复用 Schema 快照；
- 同一对象在各数据源的局部 ID 能解析到统一 `canonical_object_id`；
- 需求包含来源引用、澄清问题、冲突检查和评审记录；
- 重复提炼返回 `unchanged`，候选不会直接发布；
- 知识文档能区分 `indexed_only` 和 `candidates_created`；
- 未知、歧义、越权和空数据问题不会生成企业数值；
- 每个数值答案都有 MQL、语义版本、数据新鲜度、证据和 trace；
- 上层平台能调用结构化问数，并能绑定消息和导入一条测试反馈；
- 诊断问题返回 `analysis_run_id`，分析回执包含四步证据链与结论等级；
- 黄金问题集、确定性数值、证据完整和安全拒答门禁全部通过；
- 运行时查询回执包含映射版本、对象身份、策略、物理计划、质量和结果哈希；
- 编译指标能力不能被调用参数覆盖绑定指标；建案/通知动作通过审批与幂等校验；
- 备份恢复和语义回滚完成演练。

## 13. 常见故障定位

| 现象 | 首要检查 | 处理方式 |
| --- | --- | --- |
| 平台导入工具契约 URL 失败 | 容器是否能访问 `host.docker.internal:8000` | 从平台所在网络执行健康请求；检查防火墙与监听地址 |
| 平台工具存在但调用失败 | OpenAPI Server URL、Bearer Token | 改为调用方实际可访问的地址；检查主体权限和令牌摘要 |
| 问数返回 `needs_clarification` | 指标别名、对象范围、发布状态 | 补充问题或发布明确映射，不修改 Prompt 猜测 |
| 问数返回 `verified_no_data` | 时间范围、数据同步、对象映射 | 检查源数据和映射；不得使用示例值 |
| 语义提炼一直产生重复候选 | Schema 快照与输入哈希 | 查询 `/semantic-extraction/runs`，检查连接配置是否每次变化 |
| 同一对象跨系统查询无数据 | 对象身份注册表和源端局部 ID | 检查 `/runtime/object-identities`，确认数据源与 external ID 一致 |
| 指标能力无法调用 | 指标发布状态、能力发布状态、角色 | 检查 `/runtime/capabilities` 和调用主体；不要用参数覆盖绑定指标 |
| 建案或通知返回 403/422 | 角色、审批令牌、幂等键 | 补齐独立审批与稳定幂等键；不要重复提交随机键 |
| RCA 只有 `driver` | 上一期观测、同期事件、对象映射 | 补齐事实和事件；不要强制升级结论 |
| RCA 无法成为已验证根因 | 缺少 `causal_verification` | 由业务系统或审核流程提供核验标记与原因 |
| 平台点赞/点踩未进入 FATHOM | 消息是否先绑定、是否有反馈转发 | 检查 `message_id`、`app_id` 和回调/同步任务 |
| SSE 经代理后无输出 | 代理响应缓冲和超时 | 关闭缓冲，延长读取超时并允许长连接 |

## 14. 安全声明

数据库、工业协议和知识平台连接必须使用最小权限账号、TLS 与网络白名单。密码、令牌和 API Key 只通过环境变量、操作系统凭证库或企业密钥系统提供，不写入 YAML、源码、工作流普通变量、日志、备份或部署 ZIP。

大模型的 Base URL、模型 ID 和 API Key 属于敏感配置。生产环境应使用企业批准的模型端点，并按数据分级控制可发送上下文、日志留存和供应方数据保留策略。模型负责理解和表达，企业指标值由受权限、语义和证据约束的确定性计划计算。

备份与语义导出虽然不含密钥，仍可能包含业务对象、指标口径、数据结构、对话记录和知识文档，应按企业数据资产要求加密、授权和留存。
