# 渊渟 FATHOM 核心设计

## 一句话

FATHOM 把企业分散的数据、业务知识和运行事件编译成可验证、可计算、可治理的对象网络，为所有上层 AI 与应用提供同一套可信事实和执行边界。

## 核心判断

工业 AI 难落地，通常不是缺少模型，而是缺少模型可以稳定依赖的业务世界：对象是谁、关系是否有效、指标怎么算、数据归谁看、结论来自哪里、动作能否执行。

直接让模型面对表和 SQL，会把语义歧义、权限、口径和数据质量问题推迟到答案阶段。FATHOM 把这些问题前移到执行计划阶段：无法锚定就澄清，无法验证就阻断，只有通过校验的计划才能计算。

## 五个设计支点

1. **对象网络，而非表目录。** 对象、关系、属性、指标、事件和权限共同描述企业运行世界，贯通 IT、OT、业务、组织与空间。
2. **ABC 编译链。** Acquire 获取对象与范围，Build 绑定语义与口径，Compute 执行确定性计算。模型是翻译器，不是事实和规则的创造者。
3. **语义即契约。** 指标定义、粒度、维度、单位、Owner、数据来源和版本都可导入、导出、评测和回滚。
4. **证据先于表达。** 每个答案携带数据、语义版本、事件、质量状态、时间和 trace；自然语言只是证据之上的解释。
5. **受控演化。** Schema 发现与用户输入生成候选；用户点击发布后自动完成冲突检查和离线评测，通过即发布并可回滚，生产语义不静默变化。

## 直接价值

- 降低建设成本：从一个场景和一组真实问题反向生成最小本体，不要求业务人员先学本体语言。
- 降低维护成本：数据连接、指标、模型、工具和上层应用解耦；口径只维护一次。
- 降低学习成本：页面用业务对象、问题和证据组织流程，专业配置仍可通过 YAML 和 API 管理。
- 提高 AI 可靠性：把模型的不确定理解限制在可校验计划内，把数值计算留给确定性引擎。
- 形成复用底座：问数、BI、运营和智能体共享对象上下文、指标和权限，不重复建设语义。

## 架构

```text
上层应用与智能体
    │  OpenAPI / MCP / A2A
受控智能体网络
    │  规划 · 探索 · 解释 · 动作草案 · 证据
ABC 语义执行器
    │  对象锚定 · 指标绑定 · 权限 · 质量 · 计算
ONN 对象与语义层
    │  对象 · 关系 · 属性 · 指标 · 事件 · 权限
连接与轻量计算层
    │  SQL · 文件 · API · KV · 图 · 时序 · 向量 · 文本 · 工业协议
企业 IT / OT / 业务 / 组织 / 空间事实源
```

## 技术栈

- 后端：Python、FastAPI、Pydantic、SQLAlchemy、sqlglot
- 前端：Vue 3、TypeScript、Vite
- Lite 存储：SQLite
- 分析执行：DuckDB
- 可选向量：sqlite-vec，默认关闭
- 标准存储：PostgreSQL
- 接入：关系数据库、TDengine、MQTT、OPC UA、REST、文件、Redis、Elasticsearch、Neo4j、Qdrant
- 协议：OpenAPI、MCP、A2A
- 安全：Bearer Token 摘要、角色、对象范围、只读计划、审计和密钥引用

## 轻量化原则

默认安装只保留一套 Web 服务、一个 SQLite 文件和按需启用的 DuckDB。图关系先用关系表表达，向量默认关闭，外部大数据不搬迁。只有当并发、高可用、图遍历或向量规模确实超过 Lite 边界时，才替换对应适配器；上层 API、语义契约和使用方式不变。

FATHOM 的目标不是包办所有数据计算，而是成为企业数据与 AI 之间稳定、可信、低成本的语义控制面。
